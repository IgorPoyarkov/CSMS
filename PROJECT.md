# CSMS — система организации контрактной службы заказчика

Веб-приложение для заказчика, работающего по 44-ФЗ: план-график закупок,
контрактная служба (приказ Минфина от 31.07.2020 № 158н), задачи работников
службы, реестр контрактов и отчётность. Данные — PostgreSQL, интерфейс на
русском, светлая тема основная (как в ЕИС).

Дата описания: 2026-11-15, актуализировано 2026-11-22.

## Источник НПА — обязательное требование

Нормативные правовые акты (НПА) берутся **только** с официального
интернет-портала правовой информации `pravo.gov.ru` — это единственный источник
правды, отходить от него нельзя. Актуальная редакция документа открывается и
скачивается по ссылке вида:

`http://actual.pravo.gov.ru/content/content.html#pnum=<номер опубликования>`

Например, ПП РФ № 1875 (национальный режим):
`http://actual.pravo.gov.ru/content/content.html#pnum=0001202412250018`.

Правила по кодам ОКПД2 должны извлекаться агентом из официального текста акта
на `pravo.gov.ru`, а не зашиваться вручную и не браться из сторонних систем
(zakupki.gov.ru, КонсультантПлюс, Гарант и т.п.). `publication.pravo.gov.ru` —
поддомен того же портала и используется для первоначального официального
опубликования; актуальную редакцию отдаёт `actual.pravo.gov.ru`.

## 1. Запуск

| Команда             | Что делает                                                        |
| ------------------- | ----------------------------------------------------------------- |
| `npm start`         | Vite (:5173), PG-адаптер (:3002) и csms-api (:5099) одновременно  |
| `npm run dev`       | только фронтенд                                                   |
| `npm run pg:server` | только PG-адаптер (:3002)                                         |
| `npm run api`       | только csms-api (:5099, PostgreSQL, `EIS_STORE=postgres`)         |
| `npm run build`     | `tsc -b` и сборка в `dist/` (без обращения к БД)                  |
| `npm test`          | тесты скриптов и все проверки доменных правил (ПП, ЕИС, сроки)    |
| `npm run check:db`  | smoke-проверка `contractRegistry` из PostgreSQL через zod         |
| `npm run lint`      | линтер oxlint (в проекте используется он, не eslint)              |

База данных — PostgreSQL на `localhost:5433`, база `csms_eis`. PG-адаптер
читает данные из БД на каждый запрос, поэтому перезапуск после правок не нужен.

## 2. Стек

React 19 · TypeScript 7 · Vite 8 · react-router-dom 7 (`createBrowserRouter`) ·
@tanstack/react-query 5 · axios (база `/pg-api`, в dev проксируется на :3002) · zod 4 ·
react-hook-form 7 · SCSS-модули.

Соглашения: сервис в `src/services/<Домен>/` — `<домен>.schema.ts` (zod) +
`<домен>.api.ts` (fetch-функция и хук `useXxx`, ответы прогоняются через
`Schema.parse`); компонент в `src/components/<Домен>/` + `*.module.scss` +
`<домен>.config.ts` (справочники, подписи, форматтеры). БЭМ собирается
хелпером `useUtils().bem(styles, "block")("elem", ["mod"])`.

Состояние: серверные данные — только React Query, формы — react-hook-form,
навигация и фильтры — URL. Zustand закрывает общее UI-состояние нескольких
экранов; дублировать данные из Query в стор запрещено. Стили — только
SCSS-модули и БЭМ, Tailwind и utility-классы под строгим табу.

## 3. Кто пользователь и что ему доступно

Цепочка идентификации: `localStorage.user_email` → `useFetchCurrentUser()` →
`user.organizationId` → `useCurrentOrganization()`. Реквизиты заказчика нигде не
вводятся вручную — они берутся из организации пользователя. Все списки
отсекаются по `organizationId`.

Роль в контрактной службе определяет `useMyContractRole()`: строка штатного
расписания ищется в составе службы организации (`contractServiceRoster`).
`isHead` = роль содержит «Руководитель» или «Контрактный управляющий» — это
право назначать задачи (п. 2.4 № 158н) и оценивать их исполнение.

Тестовые учётные записи (пароли в PostgreSQL открытым текстом, кроме id 1):

| Логин             | Организация                    | Работник штатки | Роль в КС               | Право назначать задачи |
| ----------------- | ------------------------------ | --------------- | ----------------------- | ---------------------- |
| `test1@test.test` | 1 · ГБУЗ «ГКБ № 7»             | 6 Иванова А.С.  | работник службы         | нет                    |
| `test2@test.test` | 2 · Депимущество БО            | 4 Пояркова С.   | руководитель службы     | да                     |
| `test3@test.test` | 3 · МБОУ «СОШ № 15»            | 11 Тарасова Е.  | контрактный управляющий | да                     |
| `test4@test.test` | 4 · Администрация г. Белгорода | 26 Мельников А. | службы нет              | нет                    |

Сотрудник без права назначения функционал постановки задач не видит вообще —
кнопки в «Возможных действиях» просто нет.

Модуль изменения и расторжения контрактов хранит снимок контракта, правовое
основание и предлагаемые условия, комплект документов с редакциями и SHA-256,
а также журнал переходов. Статус меняется только сценариями согласования,
подписания и регистрации — отдельной кнопки «поставить статус» нет. Правила
ст. 95 44-ФЗ проверяются в csms-api; форма вызывает тот же код через
`POST /api/contract-changes/validate`. Из карточки реестра контрактов открывается
создание документа с предзаполненным снимком (`?contractId=…`).

Модуль электронного актирования (ст. 94 44-ФЗ) ведёт документ о приёмке:
снимок контракта и условий приёмки, позиции с НДС, выявленные недостатки,
итог по кодам ЕИС и журнал переходов. Поддерживаются приёмка без расхождений,
приёмка с расхождениями, мотивированный отказ и возврат на уточнение; после
подписания итога фиксируется регистрация в ЕИС. Правила (срок 1–20 рабочих
дней, экспертиза, комиссия, суммы, недостатки) проверяются в csms-api через
`POST /api/acceptances/validate`. Карточка приёмки печатает акт и связывает
документ с изменениями/расторжениями по тому же контракту; из реестра
контрактов открывается создание приёмки (`?contractId=…`).

Шапка прилипает к верху и держит сквозной контур закупки: «Главная»,
«План-график», «Потребность», «Извещения», «Контракты» и «Реестр контрактов»
с подменю. Остальные разделы (ЕИС, отчётность, справочники, справки) собраны
в меню «Ещё» из трёх колонок; на экранах уже 1040 px пункты уезжают в панель
с бургером. Справа — меню профиля (наведение или клик → «Личный кабинет» и
«Выйти») и переключатель темы. Выход есть только там — в списке рабочих
действий личного кабинета его нет, чтобы опасное действие не стояло рядом с
обычными.

Пункт «UI-решения» в шапке ведёт на `/ui-solutions` — рабочий каталог
интерфейса: 10 групп, 65 решений с назначением, местом применения и путём
реализации. Данные каталога лежат отдельно от разметки
(`src/components/UiSolutions/uiSolutions.config.ts`), поэтому перечень
правится без изменения страницы. Каталог нужен, чтобы новый экран собирался
из уже принятых решений (темы, контролы, модалки, реестры, формы), а не из
новых случайных классов.

### Личный кабинет

1. **Персональные данные** — аватар-кружок с карандашом (правка телефона и
   аватара в модалке), далее список строк «ФИО: …», должность, подразделение,
   email, телефон. Организация не показана: пользователь знает, под каким
   заказчиком он работает. Под списком — раскрывающийся подраздел «Роль в
   контрактной службе и образование (п. 2.5)».
2. **Эффективность** — суммарный и средний балл, влияние на зарплату, процент
   выполненных в срок задач и список оценок.
3. **Календарь отпусков** — собственные периоды отсутствия, а руководителю
   службы ещё табель отсутствующих по организации.
4. **Мои задачи** — фильтр по статусу со счётчиками, очередь по остатку срока,
   показ по 5 (по умолчанию) / 10 / 15 / все, вид списком (по умолчанию) или
   сеткой, переход по страницам.
5. **Возможные действия** — контрактная служба, план-график, обработка закупки,
   реестр контрактов и «Назначить задачу» (только при праве).

### Постановка задачи

Отдельная модалка. Первое поле — функция, которую назначают; исполнитель
доступен только после её выбора и заполняется списком носителей этой функции:
у службы-подразделения это работники подразделения, у службы из работников и у
контрактного управляющего — люди, которым функция надана приказом. Выбранный
срок проверяется по графику отпусков: работник в утверждённом или активном
отсутствии показан неактивным пунктом с датой окончания, а отправка задачи на
него отклоняется.

## 5. Сквозная цепочка данных

```
план-график (purchasePlan)
  └── запись плана: identificationCode (ИКЗ)
        └── закупка (procurement.ikz)
              ├── извещение (notice)
              ├── проект контракта (contractProject)
              └── реестр контрактов (contractRegistry)
                    ├── этапы (contractStages)
                    ├── платежи (contractPayments)
                    ├── неустойки (contractPenalties)
                    └── поставки (contractDeliveries)

параллельно: contractService (состав + функции раздела III)
               └── задачи (tasks.functionCode) → оценки (taskEvaluations)
               └── образование (employeeEducations, п. 2.5)
               └── отсутствие (leaves) — учитывается при постановке задачи
```

Главная считает переходы по ИКЗ и `procurementId` / `contractProjectId`, поэтому
«Поток закупки» показывает реальное число записей на каждом этапе. Сверху —
быстрые показатели (контракты, планы-графики, потребности, уведомления) и
реквизиты заказчика, ниже — все разделы, разложенные по трём группам:
планирование, исполнение и контроль, отчётность и кадры. Тяжёлые графики
Recharts и D3 вынесены на `/analytics` и грузятся отдельным чанком: главная не
импортирует их вовсе и открывается без ожидания библиотек.

Кнопка «Текущий план-график» в hero открывает карточку действующего плана
текущего года: изменённая или опубликованная редакция важнее черновика, из
нескольких версий берётся последняя. Если плана на текущий год нет — открывается
реестр планов-графиков, откуда документ и создаётся.

### Проект контракта

Конструктор на `/procurement-processing/:id/contract-project` собирает проект
по ст. 34 и 51 Закона № 44-ФЗ. Вид контракта (поставка, ремонт,
строительство/реконструкция, капремонт, стройконтроль, ПИР, содержание
услугами или работами) определяет набор разделов и приложений. Данные
предзаполняются по цепочке извещение → служебная записка → ООЗ → карточка
заказчика: предмет, цена и порядок оплаты, сроки и этапы, приёмка, качество,
обеспечения, СМП/СОНКО, сопровождение и реквизиты. Экран показывает прогресс
обязательных условий ст. 34, проверки (ошибки и предупреждения) и
предпросмотр текста контракта с приложениями.

## 7. Интерфейс и темы

Роли интерфейса объявлены в `src/scss/global/_themes.scss` и переключаются
атрибутом `data-theme` (выбор запоминается). Компоненты не используют цвета
палитры напрямую.

- Поверхности: `--surface-page` (фон страницы), `--surface-panel` (карточки и
  окна), `--surface-raised` (вложенные блоки, шапки таблиц), `--surface-accent`
  (активный элемент), `--surface-field` и `--field-border` (поля ввода).
- Границы: `--border` и `--border-strong`. В светлой теме они подняты до
  контраста не ниже 3:1 к фону (WCAG 1.4.11) — иначе контур карточки на
  «бумаге» читался как пыльная линия.
- Модалки: `--modal-border`, `--modal-dot`, `--modal-dot-glow` — рамка формы
  инвертирована к фону окна (светлая панель → тёмный контур, тёмная → светлый),
  по периметру бежит точка-маркер. Миксин `modal-frame` из
  `src/scss/global/_modal-frame.scss`; при `prefers-reduced-motion` точка
  замирает.
- Состояния: `--state-success`, `--state-danger`, `--state-warning` и мягкие
  подложки `*-soft` — отдельно от зелёной схемы сайта.
- Текстовые кнопки на акценте используют `--text-on-accent`; ранее встречался
  несуществующий `--on-accent`, из-за чего текст на тёмно-зелёной кнопке
  оставался тёмным.

## 8. Как вести задачи

Очередь задач — `CurrentTasks.md` в корне: новые формулировки добавляет
пользователь, ассистент берёт их оттуда по порядку и отмечает выполненные.
`WorkPlan.md` — юридический план по пунктам Типового положения, из него берутся
требования к сущностям. Состояние проекта — `PROJECT.md` (здесь) и служебная
заметка ассистента `.koda/PROJECT_STATE.md`.

## 9. Ограничения

- Права проверяются на клиенте: PG-адаптер отдаёт коллекции по запросу, изоляция
  обеспечена фильтрами запроса и проверками владельца в API.
- Вход — мок по email и паролю, без JWT; **вход по сертификату реализован**
  (EdsLoginForm: выбор сертификата, сопоставление с работником по ИНН/ФИО,
  login по `localStorage.user_email`, запись события в журнал ЭП).
  Подписание документов через плагин (CPSignEx) — следующий шаг.
- Реестр контрактов и отчётность СМП читают моки: обмена с ЕИС нет, ссылки на
  zakupki.gov.ru фиктивные.
- Экраны «руководитель службы» (п. 2.3 приказ о назначении как отдельный
  документ), положение о службе (п. 1.3) и штатная схема соподчинения не
  реализованы.
