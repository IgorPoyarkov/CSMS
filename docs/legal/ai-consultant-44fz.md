# ИИ-консультант по 44-ФЗ в CSMS

Проектный документ. Фиксирует договорённости: вопросы привязаны к модулям и
валидациям системы, модель работает локально, актуальность НПА поддерживаем
сами ежедневной синхронизацией с официальным порталом правовой информации.

## 1. Задача

Консультант отвечает на вопросы закупщика **в контексте того экрана, где он
работает**, и объясняет не только «как правильно», но и «почему сработала
проверка»: какая норма, какая часть статьи, какая редакция.

Три сценария:

1. **Вопрос по норме** — «можно ли изменить существенные условия контракта?»
   Ответ с цитатой и оговорками.
2. **Вопрос по данным** — «почему по контракту № 123 просрочка?» Ответ
   строится на данных CSMS через инструменты, нормы — как обоснование.
3. **Вопрос по замечанию валидатора** — «что означает это предупреждение и как
   исправить?» Ответ связывает сообщение валидатора с нормой и шагами.

Границы: это справочная система, а не юридическое заключение. В каждом ответе
— цитата первоисточника и дата редакции; при отсутствии нормы — честный отказ.

## 2. Карта «модуль → валидация → норма»

Консультант не отдельная база знаний «про всё», а слой над существующими
правилами. Каждое правило получает стабильный код и ссылку на норму; вопрос из
интерфейса приходит вместе с кодом модуля и, если есть, кодом правила.

| Модуль                         | Что проверяем                                            | Нормы                                      |
| ------------------------------ | -------------------------------------------------------- | ------------------------------------------ |
| `PurchasePlan` (план-график)   | ИКЗ, объёмы, сроки размещения, обоснование               | ст. 16–18, 21 44-ФЗ; приказ 841/пр         |
| `PurchaseNote` (СЗ, ООЗ, НМЦК) | предмет, характеристики, количество, НМЦК                | ст. 22, 33 44-ФЗ; приказ 567; 158н         |
| `Nmck`                         | методы расчёта, рыночные КП, тарифы                      | ст. 22 44-ФЗ; приказ 567                   |
| `NoticeInfo` (извещение)       | способ, сроки, преимущества, нацрежим, доптребования     | ст. 42, 49, 50 44-ФЗ; ПП 2571, 2604, 1875  |
| `ProcurementDocuments`         | комплектность, соответствие документации                 | ст. 42, 33 44-ФЗ; ПП 145, 926              |
| `ContractProject`              | обязательные условия, приёмка, ответственность           | ст. 34, 51, 94, 95 44-ФЗ; ГК РФ гл. 30, 37 |
| `ContractRegistry`             | реестровая запись, сроки публикации, исполнение          | ст. 94, 103 44-ФЗ; ПП 1042                 |
| `ContractSmp` (СМП/СОНКО)      | объём закупок у СМП, сроки оплаты, сверка с реестром МСП | ст. 30 44-ФЗ; ПП 1466                      |
| `Acceptance`                   | приёмка, экспертиза, мотивированный отказ                | ст. 94 44-ФЗ; ПП 1042                      |
| `ContractChange`               | основания изменения, допсоглашения                       | ст. 95 44-ФЗ; ГК РФ                        |
| `Reports` (158н, 238)          | сроки и состав отчётности                                | приказ 158н; ПП 238                        |
| `Notifications`                | сроки, пени, штрафы, ЕИС                                 | ст. 34, 103 44-ФЗ; ПП 1042                 |

Правило каталога:

```
rule_id          PurchaseNote.OOZ.characteristics.missing
module           PurchaseNote
severity         warning | error
message          «В ООЗ не указаны характеристики товара»
legal_ref        44-ФЗ, ч. 1 ст. 33
validator_path   src/services/ObjectDescription/order158nValidator.ts
```

Один и тот же `rule_id` используют и валидатор, и консультант. Это исключает
расхождение «форма сказала одно, чат — другое».

## 3. Синхронизация НПА

Источники (в порядке приоритета):

1. **pravo.gov.ru** — официальное опубликование: ежедневная лента за дату,
   карточка акта, полный текст, редакции.
2. **ЕИС** — изменения 44-ФЗ и подзаконных актов в сфере закупок.
3. **Минфин России** — приказы 158н, 841/пр и методические документы.

Ежедневный конвейер (cron, 05:00 МСК):

```
delta(pravo.gov.ru, date=today)
  → фильтр по перечню отслеживаемых актов
  → скачать полный текст (кэш по URL + хэш)
  → определить тип: новый акт | новая редакция | изменение
  → распарсить на статьи/части
  → записать legal_act_version (valid_from, published_at, content_hash)
  → переиндексировать чанки изменённой версии
  → отчёт в npa_sync_runs + уведомление администратору
```

Требования к конвейеру:

- **Идемпотентность.** Повторный запуск за ту же дату не создаёт дублей:
  ключ `(act_id, revision)` и сравнение `content_hash`.
- **Редакция на дату.** Храним не «текущий текст», а версии с
  `valid_from`/`valid_to`. Консультант по контракту 2024 года отвечает по
  редакции, действовавшей на дату заключения, а не по сегодняшней.
- **Бережность к источнику.** Пауза между запросами, кэш, повтор с
  экспоненциальной задержкой, уважение robots.txt и условий портала.
- **Ручное подтверждение.** Новый акт попадает в индекс только после проверки
  администратором (флаг `verified`), чтобы ошибка парсера не стала «нормой».

## 4. Схема данных (PostgreSQL)

```sql
legal_acts (
  id            bigserial primary key,
  kind          text not null,          -- federal_law | government_decree | order
  number        text not null,
  adopted_at    date not null,
  title         text not null,
  source_url    text not null,
  status        text not null default 'active',
  unique (kind, number, adopted_at)
);

legal_act_versions (
  id            bigserial primary key,
  act_id        bigint not null references legal_acts(id),
  revision      text not null,
  valid_from    date not null,
  valid_to      date,
  published_at  date,
  content_hash  text not null,
  full_text     text not null,
  verified      boolean not null default false,
  unique (act_id, revision)
);

legal_chunks (
  id            bigserial primary key,
  version_id    bigint not null references legal_act_versions(id),
  article       text,
  part          text,
  clause        text,
  text          text not null,
  token_count   int,
  embedding     vector(1024),
  tsv           tsvector
);

rule_catalog (
  id            text primary key,       -- PurchaseNote.OOZ.characteristics.missing
  module        text not null,
  severity      text not null,
  message       text not null,
  legal_ref     text not null,
  validator_path text
);

rule_legal_links (
  rule_id       text references rule_catalog(id),
  chunk_id      bigint references legal_chunks(id),
  primary key (rule_id, chunk_id)
);

npa_sync_runs (
  id            bigserial primary key,
  started_at    timestamptz not null,
  finished_at   timestamptz,
  status        text not null,          -- running | ok | failed
  added         int default 0,
  changed       int default 0,
  errors        jsonb
);

consultant_sessions (
  id            uuid primary key,
  user_id       text not null,
  organization_id bigint,
  module        text,
  entity_id     text,
  created_at    timestamptz not null default now()
);

consultant_messages (
  id            bigserial primary key,
  session_id    uuid references consultant_sessions(id),
  role          text not null,          -- user | assistant
  content       text not null,
  model         text,
  latency_ms    int,
  refusal       boolean not null default false,
  created_at    timestamptz not null default now()
);

consultant_citations (
  message_id    bigint references consultant_messages(id),
  chunk_id      bigint references legal_chunks(id),
  quote         text not null,
  primary key (message_id, chunk_id)
);
```

Индексы: `ivfflat`/`hnsw` по `embedding`, GIN по `tsv`, btree по
`(act_id, valid_from)`, GIN по `errors`.

## 5. RAG и инструменты

Пайплайн ответа:

```
вопрос + контекст экрана (module, entity_id, rule_id)
  → нормализация (сокращения, номера статей)
  → гибридный поиск: BM25 по tsv + вектор по embedding
  → отбор 8–12 чанков, дедупликация по статье
  → реранкер (bge-reranker-v2-m3)
  → 4–6 лучших фрагментов + метаданные редакции
  → локальная LLM: ответ строго по фрагментам
  → структура: summary, norms[], actions[], confidence, refusal
```

Инструменты (function calling, только чтение, с проверкой прав):

| Инструмент                              | Что отдаёт                        |
| --------------------------------------- | --------------------------------- |
| `get_contract(number\|id)`              | карточка, стороны, суммы, статус  |
| `get_contract_stages(id)`               | этапы, сроки, оплата              |
| `get_contract_payments(id)`             | платежи, статусы, даты            |
| `calc_penalty(amount, due, fact, rate)` | пени по 1/300, штраф по ПП 1042   |
| `check_smp(organizationId, year)`       | объём у СМП, сроки оплаты         |
| `get_validation_issues(entity)`         | замечания валидаторов с `rule_id` |
| `get_plan_position(ikz)`                | позиция ПГ, лимиты, ИКЗ           |
| `get_notice(id)`                        | извещение, сроки, преимущества    |

Правило: если для ответа нужен документ, а инструмент вернул пусто —
консультант говорит «данных нет», а не додумывает.

## 6. Локальная модель

Модель работает на своём железе и не отправляет данные закупок наружу. БД при
этом может быть где угодно: LLM обращается к внутреннему API, а не к базе
напрямую, поэтому расположение PostgreSQL на выбор не влияет.

| Роль             | Вариант                                    | Примечание                                       |
| ---------------- | ------------------------------------------ | ------------------------------------------------ |
| Генерация        | Qwen2.5-14B/32B-Instruct, Llama-3.1-8B/70B | русский, следование инструкциям, цитаты          |
| Эмбеддинги       | bge-m3 (1024)                              | мультиязычная, хорошо держит юридический текст   |
| Реранкер         | bge-reranker-v2-m3                         | отсекает нерелевантные чанки                     |
| Сервер           | vLLM или Ollama                            | vLLM — пропускная способность, Ollama — простота |
| Железо (минимум) | 1×A100 40 GB или 2×RTX 4090                | 14B в 8-bit; 70B — 2×A100                        |

Квантование (`awq`, `gptq`, `q8_0`) допустимо, но проверяется на золотом
наборе: качество цитат важнее скорости.

## 7. API

```
POST /api/consultant/ask
  { module, entityId?, ruleId?, question, sessionId? }
  → { answer, citations[], tools[], confidence, refusal, sessionId }

GET  /api/consultant/session/{id}      история
POST /api/npa/sync                     ручной запуск (админ)
GET  /api/npa/sync/runs                журнал синхронизаций
GET  /api/npa/diff?from=&to=           что изменилось
```

Стриминг ответа — через SSE: пользователь видит текст по мере генерации,
цитаты приходят в конце.

## 8. Безопасность и правовые ограничения

- RBAC: консультант видит только данные своей организации; инструменты
  проверяют `organizationId` так же, как обычные API.
- Аудит: вопрос, ответ, цитаты, модель и задержка пишутся в
  `consultant_messages`/`consultant_citations`.
- Персональные данные в промпт не попадают: инструменты отдают обезличенные
  поля, ФИО и контакты маскируются.
- Дисклеймер в каждом ответе: «Справочно. Проверьте первоисточник и редакцию».
- Отказ: если цитат нет или уверенность ниже порога — «в имеющихся редакциях
  ответа нет», без «примерного» ответа.

## 9. Качество

Золотой набор: 100 вопросов, по 6–10 на модуль, с эталонными цитатами.

| Метрика                                 | Цель MVP               |
| --------------------------------------- | ---------------------- |
| Доля ответов с корректной цитатой       | ≥ 95 %                 |
| Корректность ответа (экспертная оценка) | ≥ 85 %                 |
| Доля отказов вместо галлюцинаций        | ≥ 90 % спорных случаев |
| Задержка первого токена                 | ≤ 2 с (локально)       |
| Полнота индексации отслеживаемых актов  | 100 %                  |

Регрессия запускается после каждой синхронизации НПА и после смены модели.

## 10. Этапы

1. **Каркас (1–2 дня).** `rule_catalog` из существующих валидаторов, схема БД,
   сервис `npaSync`, страница `/consultant` с заглушкой.
2. **База знаний.** Синхронизация 44-ФЗ и приказа 158н, парсинг на статьи,
   индексация, ручная проверка первого среза.
3. **RAG с цитатами.** Гибридный поиск, реранкер, локальная модель, ответы со
   ссылками и отказом. Без инструментов.
4. **Инструменты CSMS.** Контракт, этапы, платежи, пени, СМП, замечания
   валидаторов. Контекстные кнопки в формах.
5. **Качество и эксплуатация.** Золотой набор, регрессия, ежедневный отчёт о
   синхронизации, редакционные срезы для старых контрактов.

## 11. Согласованные решения

Ранее открытые вопросы закрыты так:

1. **Администратор НПА** — роль `npa_admin` в контрактной службе. Подтверждает
   новые редакции, разбирает ошибки парсера, ведёт журнал. Минимум один
   человек на организацию; действия пишутся в `npa_sync_runs` и аудит.
2. **Хостинг модели** — GPU-узел заказчика (on-prem). Облачная генерация для
   данных закупок исключена; наружу уходят только запросы к внутреннему API.
3. **Режим «только нормы»** — да, флаг сессии и роли: подрядчик получает
   ответы по НПА без инструментов к данным заказчика.

## 12. Версионность НПА в интерфейсе

Версионность — не внутренняя деталь RAG, а видимая часть системы: закупщик
должен понимать, по какой редакции его проверили и что изменилось.

### 12.1. Что храним

```
акт → версии (revision, valid_from, valid_to, published_at,
               content_hash, verified, source_url)
```

Версия неизменяема: новая редакция — новая строка `legal_act_versions`.
`valid_to` проставляется при появлении следующей версии. Чанки и эмбеддинги
привязаны к версии, поэтому поиск всегда идёт по конкретной редакции.

### 12.2. Экраны

| Маршрут | Что показывает |
| --- | --- |
| `/legal` | Реестр НПА: акт, действующая редакция, дата, статус проверки, фильтры «вид», «год», «есть неподтверждённые», «есть изменения» |
| `/legal/:actId` | Карточка акта: реквизиты и источник, таймлайн версий, diff между выбранными редакциями по статьям, какие `rule_catalog` ссылаются на изменённые части, кнопка «Подтвердить версию» (только `npa_admin`) |
| `/legal/changes` | Лента синхронизаций: что добавилось/изменилось, какие правила затронуты, кто и когда подтвердил |
| `/consultant` | В каждом ответе — чип «44-ФЗ, ч. 7 ст. 34 · ред. 01.09.2026»; клик открывает карточку акта на этой версии; переключатель «на дату события / действующая» |
| Формы | Бейдж у замечания валидатора: «проверено по ред. от 01.09.2026»; если появилась новая редакция — «доступна редакция от …, проверьте» |

### 12.3. Редакция на дату события

```
legal_date(entity) =
  контракт     → contractDate
  извещение    → дата размещения
  СЗ/ООЗ       → дата проверки (для черновика — сегодня)
  приёмка      → дата акта
```

Версия выбирается как `valid_from <= legal_date < valid_to`. В интерфейсе это
написано явно: «по редакции на 12.03.2026», а не «актуально». Для старых
контрактов доступна и действующая редакция — для сравнения.

### 12.4. API

```
GET  /api/npa/acts?kind=&year=&status=
GET  /api/npa/acts/{id}
GET  /api/npa/acts/{id}/versions
GET  /api/npa/versions/{id}
GET  /api/npa/diff?fromVersion=&toVersion=
POST /api/npa/versions/{id}/verify     // npa_admin
GET  /api/npa/changes?since=
```

### 12.5. Правила отображения

- Неподтверждённая версия помечается «черновая» и **не используется** в
  ответах консультанта и в валидациях.
- Diff строится по статьям, а не по символам: «ч. 7 ст. 34 — изменена»,
  «ст. 95 — новая часть 3.1».
- Изменение, затрагивающее правило из `rule_catalog`, создаёт задачу
  администратору и подсвечивает это правило в формах.
- После подтверждения версии закупщики получают уведомление, только если
  изменения касаются используемых ими правил.

## 13. Каркас версионности (реализовано)

Порог набора редакций: **7** для федерального закона, **3** для указа,
постановления, распоряжения и приказа. Порог задан в
`src/services/LegalNpa/legalNpa.schema.ts` (`NPA_MIN_VERSIONS`) и проверяется
скриптом.

| Что | Где |
| --- | --- |
| Схема акта, версии, пороги, выбор редакции на дату, diff по статьям | `src/services/LegalNpa/legalNpa.schema.ts` |
| React Query: акты, сохранение версий, подтверждение | `src/services/LegalNpa/legalNpa.api.ts` |
| Реестр актов с прогрессом `N / required` | `/legal` — `LegalActsPage.tsx` |
| Карточка акта: таймлайн, подтверждение, сравнение редакций | `/legal/:id` — `LegalActCardPage.tsx` |
| Очередь администратора: неполные наборы и черновые версии | `/legal/changes` — `LegalChangesPage.tsx` |
| Синхронизация и проверка порога | `scripts/npa-sync.mjs` |

Команды:

```
node scripts/npa-sync.mjs --seed     # демонстрационные акты: 44-ФЗ (7), ПП 1042 (3), 158н (3)
node scripts/npa-sync.mjs --check    # порог; exit 1, если набор неполный
node scripts/npa-sync.mjs --list
node scripts/npa-sync.mjs --source=pravo --url=http://publication.pravo.gov.ru/document/0001201304080023 --act=npa-44fz
node scripts/npa-sync.mjs --source=pravo --url=… --act=npa-44fz --download
```

Что делает `--source=pravo`: читает карточку акта, извлекает номер и дату
опубликования, ссылку на PDF и на текст, добавляет редакцию с
`contentStatus: "metadata"` и обновляет дату сверки. `--download` сохраняет
PDF в `.tmp/npa/` (не коммитится).

Ограничение текущего шага: демо-набор содержит только реквизиты редакций —
тексты статей не выдумываются. Разбор полного текста и сбор всех исторических
редакций 44-ФЗ — следующий этап; до него diff по статьям честно сообщает, что
сравнивать нечего, а консультант не сможет сослаться на норму из такой версии.
