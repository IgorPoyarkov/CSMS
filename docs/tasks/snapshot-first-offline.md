# Стратегия парсинга: snapshot-first / offline-by-default

Решение пользователя от 2026-11-22: стартуем **без взаимодействия с ЕИС**.
Основная ценность на первом этапе — помощь в документах к извещению, СЗ и
проекту контракта **по данным открытого доступа**. Сервер, сертификаты и
лицензии на информационную систему подключаем только если спрос окупает
владение; тогда меняется только шаг `fetch`, а не парсеры и документы.

## Принцип

```
fetch (сеть, опционально)
  → snapshot (неизменяемый каталог + манифест: источник, дата, SHA-256)
    → parse (чистая функция без сети)
      → projection (единая read-side модель)
        → publish (API / DOCX / PDF / UI)
```

Офлайн-режим — это не «убрать фичу», а просто не вызывать `fetch`: берём
готовый снимок из `docs/snapshots/manifest.json`. Он же фиксирует, что именно
поставляется с системой и откуда взято.

## Что уже есть (фундамент)

- **Снимки НСИ** в PostgreSQL (`ref.datasets`, `EIS_STORE=postgres`):
  `nsiOKPD2` — 21 066 записей, `nsiKTRU` — 729, `order158nPool` — 41.
  Версии и SHA-256 перечислены в манифесте.
- **Правила НПА** в `csms-api`: активные версии 471-р, 926, 1875, 2604 с
  хешами исходных PDF; офлайн отдаются через `/api/npa/*`, OCR и LLM не
  запускаются при каждом старте.
- **XSD 17.0** (32 файла) закоммичены в `csms-api/schemas/17.0/`, каталог
  документации — `public/eis-schemas/catalog.json`. Это документация формата,
  а не генератор XML; на старте ничего парсить не нужно.
- **Публичная карточка контракта** (`eis-parser`, `PublicContractCardClient`)
  умеет реестровый номер, 429-повторы и WINDOWS-1251 — готовый уровень `fetch`
  без токена, но только как явной job, не в user path.
- **`ContractCardViewDto`** в eis-parser — правильный образец проекции: entity
  и кириллические поля БД не трогаются, на фронт уходит готовый DTO.

## Фаза 0 — офлайн-старт (выполнено 2026-11-22)

1. `scripts/start-api.mjs` по умолчанию выставляет `Npa__Enabled=false`,
   `EisSchemas__Update__Enabled=false`, `EisCounterparties__Update__Enabled=false`.
   Фоновые агенты больше не ходят в ЕИС и на портал публикации при старте.
   Ручные эндпоинты (`POST /api/eis/schemas/update`, импорт НСИ, синк НПА)
   остаются доступны; внешние переменные окружения имеют приоритет.
2. Манифест поставляемых снимков — `docs/snapshots/manifest.json` (версии,
   количество записей, хеши, откуда взято).
3. Потеря `payloadXml` при повторной подписи пакета (`EisPackageService.ReviseAsync`)
   проверена: исправление уже в коде — XML не пересобирается, если он настоящий;
   заглушка строится только для `placeholder-*`.

## Фаза 1 — единый контур открытых данных (впереди)

- Канонические DTO: `PurchasePlanItem`, `Notice`, `Contract`, `AcceptanceAct`,
  `Payment`, `NpaRule`. Адаптеры пишут в них из XML ЕИС, HTML публичной карточки,
  XLSX/CSV и `db.json`. Фронт не парсит XML сам.
- Один HTTP-клиент zakupki.gov.ru в csms-api вместо C#-клиента и Node-скриптов
  с разными паузами/ретраями: 429-policy, resume по реестровому номеру, прогресс.
- Контент-адресное хранилище raw: ключ SHA-256 исходного ZIP/XML/PDF; повтор
  импорта того же файла = 0 работы.
- Инкрементальность: состояние `(dataset, sourceHash, registryNumber, parsedAt)`;
  после обрыва продолжаем с того же номера, а не с начала.
- Мастер «Импорт из открытых данных» в UI: ИНН/реестровый номер → job → готовая
  проекция. Помечать в документах «Источник: открытый доступ ЕИС, снимок от …».

## Фаза 2 — производительность

- `XmlReader` вместо `XDocument.LoadAsync` всего `export.xml`; пообъектная выдача.
- Хеширование archived потока за один проход (`CryptoStream`) вместо двойного чтения.
- Общая библиотека XLSX (ZIP → `sheet1.xml` + `sharedStrings.xml`, OADate,
  ведущие нули) вместо двух почти одинаковых парсеров в `csms-api` и `eis-parser`.
- Перф-тесты на 1000 контрактов, метрики по временам phase `fetch/parse/project`.

## Фаза 3 — только по спросу

- ЕИС-шлюз за явным флагом `EIS_GATEWAY`; SOAP `getDocsIP`, токен ЕСИА,
  ГОСТ-TLS/КриптоПро, сервер и лицензии подключаются последними.
- Расчёт стоимости владения до решения о сервере/сертификатах.

## Почему это безопасно для текущих проверок

Фаза 0 не меняет доменные сущности, схемы БД, DTO и формы: только значения
окружения при запуске через `npm start`/`npm run api` и служебные документы.
Ручные обновления и уже опубликованные версии остаются на месте.
