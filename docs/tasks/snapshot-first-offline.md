# Стратегия парсинга: snapshot-first / offline-by-default

Решение пользователя от 2026-11-22: стартуем **без взаимодействия с ЕИС**.
Основная ценность на первом этапе — помощь в документах к извещению, СЗ и
проекту контракта **по данным открытого доступа**. Сервер, сертификаты и
лицензии на информационную систему подключаем только если спрос окупает
владение; тогда меняется только шаг `fetch`, а не парсеры и документы.

## Принцип

```
fetch (сеть, опционально)
  → snapshot (неизменяемый каталог + манифест: источник, дата, SHA-256)
    → parse (чистая функция без сети)
      → projection (единая read-side модель)
        → publish (API / DOCX / PDF / UI)
```

Офлайн-режим — это не «убрать фичу», а просто не вызывать `fetch`: берём
готовый снимок из `docs/snapshots/manifest.json`. Он же фиксирует, что именно
поставляется с системой и откуда взято.

## Что уже есть (фундамент)

- **Снимки НСИ** в PostgreSQL (`ref.datasets`, `EIS_STORE=postgres`):
  `nsiOKPD2` — 21 066 записей, `nsiKTRU` — 729, `order158nPool` — 41.
  Версии и SHA-256 перечислены в манифесте.
- **Правила НПА** в `csms-api`: активные версии 471-р, 926, 1875, 2604 с
  хешами исходных PDF; офлайн отдаются через `/api/npa/*`, OCR и LLM не
  запускаются при каждом старте.
- **XSD 17.0** (32 файла) закоммичены в `csms-api/schemas/17.0/`, каталог
  документации — `public/eis-schemas/catalog.json`. Это документация формата,
  а не генератор XML; на старте ничего парсить не нужно.
- **Публичная карточка контракта** (`eis-parser`, `PublicContractCardClient`)
  умеет реестровый номер, 429-повторы и WINDOWS-1251 — готовый уровень `fetch`
  без токена, но только как явной job, не в user path.
- **`ContractCardViewDto`** в eis-parser — правильный образец проекции: entity
  и кириллические поля БД не трогаются, на фронт уходит готовый DTO.

## Фаза 0 — офлайн-старт (выполнено 2026-11-22)

1. `scripts/start-api.mjs` по умолчанию выставляет `Npa__Enabled=false`,
   `EisSchemas__Update__Enabled=false`, `EisCounterparties__Update__Enabled=false`.
   Фоновые агенты больше не ходят в ЕИС и на портал публикации при старте.
   Ручные эндпоинты (`POST /api/eis/schemas/update`, импорт НСИ, синк НПА)
   остаются доступны; внешние переменные окружения имеют приоритет.
2. Манифест поставляемых снимков — `docs/snapshots/manifest.json` (версии,
   количество записей, хеши, откуда взято).
3. Потеря `payloadXml` при повторной подписи пакета (`EisPackageService.ReviseAsync`)
   проверена: исправление уже в коде — XML не пересобирается, если он настоящий;
   заглушка строится только для `placeholder-*`.

## Фаза 1 — единый контур открытых данных (впереди)

- Канонические DTO: `PurchasePlanItem`, `Notice`, `Contract`, `AcceptanceAct`,
  `Payment`, `NpaRule`. Адаптеры пишут в них из XML ЕИС, HTML публичной карточки,
  XLSX/CSV и `db.json`. Фронт не парсит XML сам.
- Один HTTP-клиент zakupki.gov.ru в csms-api вместо C#-клиента и Node-скриптов
  с разными паузами/ретраями: 429-policy, resume по реестровому номеру, прогресс.
- Контент-адресное хранилище raw: ключ SHA-256 исходного ZIP/XML/PDF; повтор
  импорта того же файла = 0 работы.
- Инкрементальность: состояние `(dataset, sourceHash, registryNumber, parsedAt)`;
  после обрыва продолжаем с того же номера, а не с начала.
- Мастер «Импорт из открытых данных» в UI: ИНН/реестровый номер → job → готовая
  проекция. Помечать в документах «Источник: открытый доступ ЕИС, снимок от …».
- ⚠️ **Проверка 2026-11-22: поиск ЕИС игнорирует фильтр по ИНН.** Запросы
  `customerINN=…`, `customerInn=…` и `customerIdOrg=…` к
  `/epz/contract/search/results.html` отдают одну и ту же общую выдачу
  («более 52 000 000 записей»). Поэтому `--inn` не является надёжным источником
  списка контрактов: 186 проекций из пробного обхода `inn-full-2026-v2`
  принадлежат другим заказчикам (ни одна не содержит ИНН `4629040439` и не
  совпадает с 523 контрактами в БД), в импорт они не годятся. Источник списка —
  уже известные реестровые номера из `contractRegistry` или явный ручной список;
  по ним карточки парсятся точечно и попадают в уже существующие коллекции.
- **Курсор импорта (решение пользователя 2026-11-22).** Большой проход по ИНН
  делается **один раз**. Дальше хранится последний успешно разобранный реестровый
  номер; раз в день поиск по ИНН перечисляет номера за год, и парсятся только те,
  что старше курсора. **Та же схема применяется ко всем наборам данных**: реестр
  контрактов, план-график, извещения, карточки приёмки/оплаты. У каждого набора —
  свой курсор и время последней проверки; новый номер → только он и попадает в
  `parse`. Реализация для карточек: `eis-parser` `--incremental` + `--state`
  (по умолчанию `<out>/import-state.json`). Если state ещё нет, а в `--out` уже
  лежат проекции прошлого полного прохода, курсор восстанавливается из них без
  сети. Курсор двигается только после успешного разбора, поэтому упавший номер
  повторяется на следующей проверке. При отсутствии новых номеров шаг `parse`
  вообще не вызывается — только дешёвый HTML-поиск и обновление времени проверки.
- **Ручной запрос по номеру и периоду.** Если пользователь знает, что извещение
  или контракт уже зарегистрированы в ЕИС, он должен иметь возможность запросить
  их явно (реестровый номер + год/период) и получить проекцию в систему без
  ожидания ежедневной проверки. Режимы реализованы:
  `--contract-card <реестровый номер> --year <год>` (eis-parser),
  `--plan-number <номер> --year <год>` и `--notice-number <номер> --year <год>`
  (Node-импорт). Явный номер парсится независимо от курсора и не откатывает его
  назад; при инкременте/ручном запросе существующие записи не удаляются, а
  перекрываются по номеру.

### Карточки по своим номерам (рекомендуемый путь)

Поскольку поиск ЕИС игнорирует фильтр заказчика, список номеров берём из своей
БД, а не из `--inn`. Один раз выгружаем номера из `contractRegistry`, затем
парсим их явным списком. `--numbers-file` принимает по одному 19-значному
номеру в строке (пустые строки и `#`-комментарии игнорируются); с `--incremental`
уже готовые `*.json` пропускаются, так что обрыв можно продолжить.

```powershell
# 1. Список реестровых номеров из своих контрактов (из PG).
node --input-type=module -e "import {createPgPool,loadDbFromPg} from './scripts/lib/pg-store.mjs'; const p=createPgPool(); const c=await p.connect(); const db=await loadDbFromPg(c); const s=new Set(); for (const x of db.contractRegistry) { const m=String(x.eisUrl??'').match(/reestrNumber=(\d{19})/); if (m) s.add(m[1]); if (/^\d{19}$/.test(String(x.eisRegistryNumber??''))) s.add(String(x.eisRegistryNumber)); } c.release(); await p.end(); console.log([...s].sort().join('\n'));" > our-numbers.txt

# 2. Парсинг карточек (только явные номера, без обращения к поиску ЕИС).
dotnet run --project eis-parser/src/Eis44Parser.Worker --no-build -- `
  --numbers-file our-numbers.txt --year 2026 --out <каталог-проекций> --incremental

# 3. Импорт проекций на фронт: полный DTO в коллекцию contractCardProjections.
node scripts/import-contract-card-projections.mjs --dir <каталог-проекций> --dry-run
node scripts/import-contract-card-projections.mjs --dir <каталог-проекций>
```

Импорт точечный (upsert по реестровому номеру), ничего не очищает. По умолчанию
пропускаются проекции, которые не удалось связать ни с одним контрактом из
`contractRegistry` (ни по реестровому номеру, ни по номеру контракта из актов);
`--allow-unmatched` включает их импорт явным решением пользователя. Проекции
не являются entity: все поля `ContractCardViewDto` (`Acts`, `Decisions`, `Payments`,
`Messages`, `Executions`, `SkippedFiles`) лежат на верхнем уровне документа и
отдаются через `/contractCardProjections` так же, как и другие коллекции PG.

### Команды ежедневной проверки (поиск по ИНН — только для справки)

```powershell
# Карточки приёмки/оплаты: полный проход, затем только курсор.
dotnet run --project eis-parser/src/Eis44Parser.Worker --no-build -- `
  --inn 4629040439 --year 2026 --limit 1000 --out <каталог-проекций>
dotnet run --project eis-parser/src/Eis44Parser.Worker --no-build -- `
  --inn 4629040439 --year 2026 --out <каталог-проекций> --incremental

# План-график и извещения: полный проход, затем ежедневный инкремент.
node scripts/import-eis-client.mjs --inn 4629040439 --years 3 `
  --plans 3 --notices 3 --notice-years 2
node scripts/import-eis-client.mjs --inn 4629040439 --incremental

# Список реестра контрактов: полный проход, затем ежедневный инкремент.
node scripts/import-contract-registry.mjs --inn 4629040439 --year 2026
node scripts/import-contract-registry.mjs --inn 4629040439 --incremental

# Ручной запрос известных номеров в оговоренном периоде.
node scripts/import-eis-client.mjs --inn 4629040439 --plan-number <номер> --year 2026
node scripts/import-eis-client.mjs --inn 4629040439 --notice-number <номер> --year 2026
node scripts/import-contract-registry.mjs --reestr-number <реестровый номер> --year 2026
dotnet run --project eis-parser/src/Eis44Parser.Worker --no-build -- `
  --contract-card <реестровый номер> --year 2026 --out <каталог-проекций>
```

Состояние Node-импорта лежит в `%TEMP%/csms-eis-import-state.json`
(переопределяется `--state`), у карточек — в `<out>/import-state.json`.
В state хранятся отдельные курсоры `contractRegistry`, `purchasePlans` и
`notices` и время последней проверки. Парсер выдачи реестра контрактов
(`scripts/lib/contract-registry-search.mjs`) чистый и умеет разбирать локальный
снимок через `--html-file` — проверка разметки не требует сети и не пишет в БД
при `--dry-run`. Если новых номеров нет, дешёвый поиск завершается без разбора
карточек и без перезаписи данных. При первом инкременте без state курсор
берётся из максимального номера уже импортированных записей (для карточек — из
готовых `*.json` в `--out`), то есть повторного большого прохода не требуется.

## Фаза 2 — производительность

- `XmlReader` вместо `XDocument.LoadAsync` всего `export.xml`; пообъектная выдача.
- Хеширование archived потока за один проход (`CryptoStream`) вместо двойного чтения.
- Общая библиотека XLSX (ZIP → `sheet1.xml` + `sharedStrings.xml`, OADate,
  ведущие нули) вместо двух почти одинаковых парсеров в `csms-api` и `eis-parser`.
- Перф-тесты на 1000 контрактов, метрики по временам phase `fetch/parse/project`.

## Фаза 3 — только по спросу

- ЕИС-шлюз за явным флагом `EIS_GATEWAY`; SOAP `getDocsIP`, токен ЕСИА,
  ГОСТ-TLS/КриптоПро, сервер и лицензии подключаются последними.
- Расчёт стоимости владения до решения о сервере/сертификатах.

## Почему это безопасно для текущих проверок

Фаза 0 не меняет доменные сущности, схемы БД, DTO и формы: только значения
окружения при запуске через `npm start`/`npm run api` и служебные документы.
Ручные обновления и уже опубликованные версии остаются на месте.
