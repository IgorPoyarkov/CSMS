# Альтернативная интеграция ЕИС через ЛК (логин/пароль) — подготовка

Статус: **подготовка**. Сеть не вызывается, учётных данных в репозитории нет.
Это уточнение пункта A2 (`docs/tasks/eis-chain-readiness.md`) и Фазы 3
(`docs/tasks/snapshot-first-offline.md`): вместо регистрации нашей платформы
в реестре ВС можно отправлять пакеты от имени сотрудника заказчика, используя
технические логин/пароль, выданные в его личном кабинете ЕИС.

## Границы: что это даёт, а что нет

- **Даёт:** исходящую отправку сведений (извещения, контракты, исполнение,
  акты, платежи), транспортную квитанцию с GUID, опрос статуса, протокол ФЛК
  и его ошибки — всё от имени конкретного заказчика.
- **Не даёт:** массового чтения реестра. Это не замена публичной карточки и не
  источник для `formingDocuments`: снимок → разбор → проекция остаются как
  есть. Меняется только шаг `publish`.
- **Отличается от полной интеграции ВС:** нашу платформу не регистрируют в
  реестре ВС; запросы авторизуются технической парой ЛК заказчика. Но
  ответственность за корректность отправленных сведений остаётся на заказчике
  и на том, кто формирует XML.
- Флаг включения — `EisGateway__Enabled=true` (в коде — `EIS_GATEWAY`). По
  умолчанию выключено; `scripts/start-api.mjs` задаёт безопасные значения.

## Что уже есть в проекте (не надо переписывать)

- `src/services/Eis/eisPackages.schema.ts`: статусы `Draft → Signing → Signed →
  SentToEis → FlkChecking → AcceptedInLk / RejectedByFlk / SendFailed`, поля
  `eisGuid`, `flkErrors`, `history`, `payloadXml`, `payloadSha256` — жизненный
  цикл из описания ЕИС уже совпадает с нашей моделью пакета. Новых статусов не нужно.
- `src/services/Eis/eisPackages.api.ts`: подписание, прикрепление подписи,
  отправка, опрос pending-пакетов раз в 5 секунд; шлюз живёт в соседнем
  репозитории `csms-api` (порт 5099).
- XSD Альбома 17.0 (32 файла) и каталог `/eis/schemas` — база для валидации
  XML до отправки.
- Проекции публичной карточки (`contractCardProjections`) уже содержат все
  поля актов/оплат/этапов для формирования документов — источник данных для
  будущих пакетов `ContractExecution`.
- В `eis-parser` есть XSD/WSDL НСИ и SOAP-клиент — отправной материал для
  транспортного конверта.

## Что нужно получить от заказчика до написания реального транспорта

1. Сотрудник ЛК с правом формировать и размещать сведения о контрактах. В ЛК:
   «Администрирование → Пользователи организации → Регистрационные данные»
   (или «Личный кабинет → Редактировать данные пользователя») → ссылка
   «Данные пользователя для альтернативной интеграции (по протоколу HTTPS)».
2. Сгенерированная парой логин/пароль, дата выдачи, срок действия, ФИО
   ответственного. Пароль хранится только в зашифрованном виде (User Secrets
   на разработке, KMS/мастер-ключ в проде), в логах и репозитории — никогда.
3. Доступ к тестовому контуру шлюза (или согласованный порядок проверки),
   иначе нельзя подтвердить ни конверт, ни ФЛК.
4. Актуальные WSDL/XSD и ТФФ из раздела ЕИС «Информационные материалы»
   с указанием версии и даты: методы приёма пакета, проверки статуса,
   получения протокола, формат квитанции, способ авторизации (HTTP Basic
   или `UsernameToken` в SOAP — зависит от версии интерфейса).
5. Решение по ГОСТ Р 34.10-2012 / 34.11-2012: КриптоПро CSP + ЭЦП SDK,
   либо stunnel с gost-engine, либо локальный агент на ПК заказчика. Для
   старта рекомендуется локальный агент: сертификаты и пароли не уезжают
   на наш сервер.
6. Лимит размера пакета и порядок загрузки крупных вложений в файловый
   сервис; кто и где хранит отсоединённую подпись CMS/PKCS#7.

## Контракт конфигурации (без секретов в репозитории)

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `EisGateway__Enabled` | `false` | Включает сетевой транспорт; без него любые отправки запрещены |
| `EisGateway__Transport` | `mock` | `mock` / `soap`; mock ничего не отправляет |
| `EisGateway__Endpoint` | — | URL шлюза (только HTTPS) |
| `EisGateway__Login`, `EisGateway__Password` | — | Техническая пара ЛК; User Secrets / KMS, не appsettings.json |
| `EisGateway__AuthMode` | `soap-username-token` | Уточнить по WSDL: `http-basic` или `soap-username-token` |
| `EisGateway__TlsMode` | `local-agent` | `local-agent` / `gost-tunnel` |
| `EisGateway__SchemaVersion` | `17.0` | Версия XSD, совпадает с каталогом схем |
| `EisGateway__PollIntervalMs` | `15000` | Интервал опроса GUID пакета |

Проверка конфигурации вынесена в `scripts/lib/eis-gateway.mjs` и покрыта
офлайн-тестами (`npm run test:scripts`): при выключенном флаге отправитель
не делает ни одного сетевого вызова, а диагностика никогда не печатает
значения логина/пароля.

## Жизненный цикл пакета → уже существующие статусы

| Шаг из описания ЕИС | Наш статус | Что сохраняем |
|---|---|---|
| XML собран, подпись не приложена | `Draft` | `payloadXml`, `payloadSha256`, снимок заказчика |
| Подпись локального провайдера | `Signing` → `Signed` | `signatureBase64`, `signerThumbprint` |
| `send`, получена транспортная квитанция | `SentToEis` | `eisGuid`, время отправки |
| Опрос `getStatus` по GUID | `FlkChecking` | историю попыток |
| Протокол приёма без ошибок | `AcceptedInLk` | номер/дату из протокола |
| Протокол с ошибками валидации | `RejectedByFlk` | `flkErrors[]` с кодами и подсказками |
| Транспортная/сертификатная ошибка | `SendFailed` | текст ошибки без секретов |

## План подготовки (без учётных данных)

| Этап | Работа | Готовность |
|---|---|---|
| P0 | Контракт конфигурации, заготовка SOAP-конверта, разбор квитанции, офлайн-тесты, этот документ | **сделано в этой ветке** |
| P1 | Получить WSDL/ТФФ, подтвердить способ авторизации и структуру квитанции, сгенерировать клиент, включить XSD-валидацию 17.0 до отправки | ждёт документов ЕИС |
| P2 | Локальный агент с ГОСТ-TLS, health-check туннеля, проверка срока сертификата | ждёт решения по криптопровайдеру |
| P3 | Реальные `send / receive / getStatus`, запись GUID и ошибок ФЛК в пакет, индикация в UI | ждёт тестового контура |
| P4 | Профили на каждого заказчика, ротация пароля, шифрованное хранилище, уведомление об истечении | ждёт спроса |

## Риски

- WSDL/XSD обновляются несколько раз в год: версию фиксируем в конфиге и
  прогоняем XSD-валидацию перед отправкой, а не «на глаз».
- Пароль ЛК имеет срок действия: нужна проверка и уведомление заранее.
- Подпись и отправка идут от имени сотрудника заказчика: в интерфейсе это
  должно быть явно видно, чтобы не подписать чужим сертификатом.
- Пакеты больше 10–50 МБ идут через отдельный файловый сервис; текущий
  транспорт такого разделения не делает — это отдельная задача P3.

## Что не меняем

Доменные сущности, кириллические колонки БД, существующие статусы пакета без
необходимости и офлайн-старт. Парсинг открытых данных остаётся job по явным
реестровым номерам (`--numbers-file`) и не зависит от появления шлюза.
