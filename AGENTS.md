# Инструкции для AI-агентов

С этим репозиторием работают несколько агентов: локальный (Koda в VS Code)
и облачный (Google AI Studio через GitHub). Правило ниже защищает от потери
работы, когда два агента не видят правки друг друга.

## Синхронизация git — обязательный порядок работы

1. **Перед началом любой задачи** — выполнить `git pull` и посмотреть, что
   прилетело из GitHub. Продолжать работу только от актуального состояния.
2. **После завершения работы** — закоммитить и запушить все изменения
   (`git add -A`, `git commit`, `git push`). Не оставлять незакоммиченных
   правок на моменте, когда задача передаётся другому агенту.
3. **После pull чужих изменений** — прогнать проверки:
   `npx tsc -b`, `npx oxlint src`, `npx vite build`. Если проверки падают
   на файлах, которых не касался текущий агент, — не «чинить их по пути»,
   а сообщить пользователю: это чужая незавершённая работа.
4. Незавершённые блоки помечать в сообщении коммита (как сделано для
   нормирования в `837898a`), чтобы следующий агент не принял их за готовые.

## Контекст проекта

- **Первым читать `.koda/PROJECT_STATE.md`** — служебная заметка о текущем
  состоянии: команды и проверки, ловушки zod, счётчики коллекций, учётки,
  домены и бизнес-правила, итоги последних проверок и очередь следующей
  сессии. После завершённой работы файл надо обновить (иначе следующий агент
  будет работать по устаревшим фактам).
- Задачи и решения: `CurrentTasks.md`, `PROJECT.md`, `WorkPlan.md` — читать
  перед работой по функционалу, там зафиксированы договорённости.
- Стек: React 19 + TypeScript + Vite, SCSS-модули, react-hook-form + zod,
  @tanstack/react-query, axios. Данные — PostgreSQL: PG-адаптер
  (`npm run pg:server`, порт 3002) и csms-api (порт 5099).
- **Стили — только SCSS-модули и БЭМ.** Tailwind, utility-классы и
  `@import "tailwindcss"` категорически запрещены (жёсткое табу): стили
  пишутся в `*.module.scss`, классы собираются хелпером
  `useUtils().bem(styles, "block")("elem", ["mod"])`. Файл `src/index.css`
  с импортом Tailwind удалён, не возвращать.
- **Кастомные UI-компоненты обязательны.** Если для элемента интерфейса в
  `src/components/UI/` есть готовый компонент — нативный аналог использовать
  нельзя:
  - `Select` вместо `<select>` (нативный список в тёмной теме рисует браузер);
  - `CustomCheckbox` / `CustomRadio` вместо `<input type="checkbox"|"radio">`;
  - `CustomInput`, `MoneyInput` вместо «голого» `<input>`;
  - `CustomButton` вместо стилизованного `<button>`;
  - `CustomModal` вместо самодельных оверлеев и порталов;
  - `Loader` вместо текста «Загрузка…»;
  - `PageSizePicker` для выбора размера страницы, `Okpd2Select` / `KtruSelect` /
    `OkeiSelect` / `CounterpartySelect` / `AddressCascade` — для
    соответствующих справочников.
  Нативный контрол допустим только **внутри** самого кастомного компонента
  (скрытый input для доступности и react-hook-form) и в местах, где проект
  осознанно оставил нативное поведение — такое место комментируется в коде.
  Если готового компонента нет, сначала добавить его в `UI/` и переиспользовать,
  а не писать локальную копию в фиче.
- **Состояние.** Серверные данные живут только в `@tanstack/react-query`
  (React Query — это и есть наш стор для данных), формы — в react-hook-form,
  навигация/фильтры — в URL. Общее UI-состояние, используемое более чем одним
  экраном, выносится в Zustand; локальный `useState` для одного компонента
  нормален. Не дублировать данные из React Query в стор — это источник
  рассинхрона, а не ускорения.
- Комментарии в коде — на русском, стиль существующих файлов сохранять.

## Правила преобразования НПА в карточки

НПА в системе показывается не сплошным текстом, а структурированным
документом. При любом преобразовании акта в карточку/просмотр — из статического
каталога, из csms-api или в ответе консультанта — соблюдать:

- **Текст.** Только дословная редакция с `pravo.gov.ru`: не пересказывать, не
  сокращать, не «исправлять» нумерацию и пунктуацию. LLM/OCR без отдельного
  одобрения не применять.
- **Форматирование и структура.** Официальные заголовки и номера получают
  отдельные блоки: акт/редакция → раздел/глава → статья → часть → пункт →
  подпункт/абзац. Добавочные номера (`24.1`, `4.1`, `6.1`) сохраняются целиком.
  Разметка только подчёркивает структуру: если уровень определить нельзя, текст
  остаётся как есть и помечается на проверку; выдуманные заголовки и якоря
  запрещены. Пустые маркеры удалённых пунктов в структуру не попадают.
- **Навигация внутри акта — всегда.** Оглавление не зависит от дополнительных
  действий пользователя и содержит переходы ко всем уровням, которые реально
  есть в документе: от минимального (пункт/подпункт) до максимального
  (глава/раздел и сам акт с редакциями). Активный раздел подсвечивается,
  глубокие ссылки на норму (`#якорь`, `ref=…`) работают.
- **Навигация во внешний НПА.** Если есть официальная карточка/текст на
  `pravo.gov.ru` или акт ссылается на другой НПА с известным адресом, в карточке
  должны быть переходы на него (новая вкладка, `rel="noreferrer"`). Нет адреса —
  показывается честный статус «нет официальной карточки», а не выдуманная ссылка.
- **Единый вид карточки.** Карточки актов из всех источников имеют одинаковую
  разметку, группы и сортировку; акт не дублируется, если он уже представлен в
  каталоге.
